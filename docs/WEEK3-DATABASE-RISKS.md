# Week 3 Phase 1: Database and Migration Risks

**Status:** historical pre-implementation planning register. Ratings are qualitative design assessments, not measured probabilities. The risks below record the original design analysis; implementation outcomes and remaining limits are documented in [WEEK3-EF-IMPLEMENTATION.md](WEEK3-EF-IMPLEMENTATION.md).

| Risk | Current evidence / impact | Planned control before implementation |
|---|---|---|
| Historical transaction times are unknown | Every one of the 40 transactions in the inspected `App_Data/counter-transactions.json` lacks `OccurredAtUtc`; current reports intentionally exclude them from date-based totals. Fabricated timestamps would misstate sales. | Import as `NULL`, preserve original JSON and report excluded counts. Only backfill from verifiable external evidence through a separately approved audited correction. |
| Local JSON snapshot may not be complete | `shipments.json` and `money-orders.json` are absent from the inspected data directory although repositories/workflows support them. Absence does not prove no historical rows exist elsewhere. | Discover all configured data directories and backups before migration. Treat absence as an unresolved source question, not a zero-row assertion. |
| Polymorphic line references | `TransactionLineItem.ReferenceId` means SKU for retail and shipment ID for shipment service; money-order service lines currently have no ID reference. A simple FK cannot preserve this polymorphism. | Preserve source text, map only verified typed references, report unresolved references, and keep sale-time line snapshots. Never guess a target FK. |
| Computed and captured money values can disagree | JSON transaction records include stored totals and lines/tax-rate snapshots; the domain exposes calculated values. A mismatch could alter receipts or financial reports. | Dry-run compare stored totals with deterministic recomputation. Quarantine discrepancies for review; preserve both original values until an approved rule decides which value is authoritative. |
| JSON serialization may change silently | JSON uses wrapped value objects, string enums, private setters/JSON inclusion, case-insensitive reads and constructor binding. Changes to constructors or serialization options can break the source parser. | Freeze an importer version and sanitized compatibility fixtures. Validate each real file with a read-only importer; do not deserialize and re-save the originals. |
| Source corruption or duplicate data | Current snapshot checks found no duplicate identifiers in available collections, but missing files and unexamined alternate data paths mean this is not a full operational guarantee. Malformed JSON or duplicate keys can abort reads today. | Hash and backup every source, parse all files before target writes, validate required keys/FKs/amounts, stop on any unexplained error, and produce aggregate-only diagnostics. |
| Sensitive data exposure | `staff-credentials.json` contains PBKDF2 password hashes; staff and money-order data may include personal information; identity verification is masked by domain validation. | No sensitive values in docs, console output, audit, or migration manifests. Limit database/backup access. Keep credentials separate. Accept only the masked identity value; never add a full document number field. |
| Partial sale writes / business regression | Current JSON sale writes inventory, shipment, money order and transaction in separate operations and compensates on ordinary failures. SQL refactoring can accidentally change business order, notifications, totals, or PRG behavior. | Move the business unit to one SQL commit; add failure-injection and LocalDB tests for rollback; run all existing tests and Web integration cases. Keep notification side effects after commit. |
| Reversal stock double-restore or lost restore | Current protection uses a process-wide semaphore and repository-local set. It is not durable across process restart or multiple processes. SQL row updates without an atomic transaction could recreate this failure. | Commit reversal status, stock change and unique reversal movement marker atomically; use rowversion and stock nonnegative predicates. Test same-process retries, concurrent attempts, process restart semantics and rollback. |
| Concurrent stock changes / lost update | Current file locks are in-process only; multi-process JSON deployments can overwrite each other. SQL read/modify/write without concurrency handling can oversell or lose adjustments. | Conditional quantity decrement, `BranchStock.rowversion`, unique composite key and transaction rollback; test simultaneous sales and adjustments against SQL Server. |
| Audit and business transaction boundaries | Current audit filter writes after MVC action completion and catches/logs audit failures. Making audit a required part of a business transaction could turn a completed sale into a failed response or falsely signal saved evidence. | Keep append-only SQL audit write separate by default; log a clear failure and never claim it succeeded. If fail-closed semantics are later mandated, decide explicitly before implementation and define recovery. |
| Audit privacy / overcollection | Generic route IDs or form bodies could capture sensitive data; route value meaning varies by controller. | Keep action-specific identifier allowlists; do not serialize request bodies, passwords, tokens, API keys, card data or identity values. Keep audit append-only and test output values. |
| Staff/role drift during authorization | Cookie claims may be stale after staff deactivation or branch/role change; current reversal service reloads current staff. Mapping roles and branch FKs incorrectly could weaken authorization. | Preserve current-staff checks and branch rules; map stable role codes and test inactive staff, changed role/home branch, clerk denial, manager branch restriction and administrator path. |
| Audit history lacks actor for legacy rows | Existing JSON business entities generally do not record `CreatedBy`; action audit is separate and incomplete for some action types. | Keep `CreatedBy` nullable for legacy rows. Do not infer actors from current staff data or an unrelated audit entry. Record the migration operator only for the migration event itself. |
| Financial history could be deleted via cascade | Cascading delete from branch/staff/product to transaction/audit data would destroy history. | Use `NO ACTION`/restrict relationships and deactivate/reference-data retention. Never cascade-delete transactions, payments, money orders, movements, verifications or audit entries. |
| SQL model could distort Domain | `Money`, `BranchCode`, `Sku`, private transaction line collections and nested verification do not have EF-specific keys/setters. Adding EF attributes or changing behavior for mapping convenience would leak persistence. | Configure converters and Fluent mappings in Infrastructure; use a small persistence entity/mapper for the awkward aggregate graph. No EF dependencies in Domain/Application. |
| ORM tracking can cause hidden extra writes | Repository methods that call `SaveChangesAsync` independently would violate one use-case boundary; tracking every report entity can increase memory and writes. | Repositories stage changes only. One scoped DbContext is shared per use case; one explicit Unit of Work commit. Use `AsNoTracking` DTO projections for reports and reads. Never expose `IQueryable`. |
| LocalDB portability and operational limits | This audit machine has LocalDB installed, but other developer/CI machines may not. LocalDB is intended for local development, not assumed production hosting. | Document Windows/LocalDB prerequisites, isolate test DB names, keep connection secrets in user-secrets, and choose production SQL Server hosting separately. Fail fast with a clear configuration error. |
| Test data may touch real local data | `App_Data` contains local demo records, including credential hashes; tests or seed tasks aimed at default paths could mutate it. | Every integration test and importer rehearsal uses a unique temporary directory/database. Never point seed/import/test tools to actual `App_Data`; verify source hashes before and after a dry run. |
| Rollback after cutover may lose writes | Switching back to JSON after SQL starts accepting writes returns to a stale snapshot. | Retain immutable source backup; rollback to JSON only before SQL writes. After cutover, require a tested reverse-delta/restore plan and explicit operator decision. Avoid dual writes. |
| Indexes may add cost without benefit | The proposed composite indexes are hypotheses; no SQL plans or logical reads exist yet. Additional indexes increase insert/update cost and storage. | Gather representative plans, logical reads and CPU in the later performance phase. Add/retain only measured indexes. Do not turn local cache timings into database-performance claims. |
| Missing durable shipment event history | Current Shipment stores only the latest courier status and update time; no tracking event collection exists. | Preserve current behavior in initial migration. Add event history only if a confirmed requirement needs it; do not infer or fabricate historical events. |
| Full payment/refund integration is not modeled | Current `PaymentMethod` is on the transaction, and refund is a full-state transition without a payment-provider action. | `Payments` is an assignment-driven table for the simulated single full payment. Do not imply money movement or add partial refund/provider fields without new scope. |
| SyncInbox can imply unapproved offline functionality | The trainer excluded Couchbase Lite, Counter Terminal and offline synchronization from this implementation scope. | Defer physical `SyncInbox` migration and synchronization behavior. Keep the requirement visible here and in the schema proposal; mark it not implemented. Ask for the Week 3 scoring rubric before estimating assessment impact. |
| Assessment impact is unknown | The supplied `apexpost.txt` contains the Week 2 assessment only and no Couchbase/offline marks. | Do not claim those marks are satisfied or remove the area from analysis. Request the actual Week 3 rubric before making a score/coverage statement. |

## Open decisions for Phase 2 approval

1. Confirm which local data directory is authoritative and whether another preserved directory/backup contains shipment or money-order JSON.
2. Decide whether `StockMovements` is required for stock adjustment history and reversal idempotency; current `AuditActionRecord` does not include adjustment quantity.
3. Confirm email case/uniqueness behavior, table field-size policy, and whether business codes can be renamed.
4. Decide whether a transaction may contain more than one money order or shipment before adding unique transaction constraints.
5. Confirm how the original transaction JSON totals should be handled if they do not equal recomputed snapshots.
6. Obtain the actual Week 3 Couchbase/offline assessment criteria; current trainer instruction still excludes implementation.
7. Approve development/test database lifecycle, backup location, and post-cutover rollback policy.

## Explicit exclusions

No Couchbase Lite, Counter Terminal, offline synchronization, SyncInbox processing, production cloud database, payment gateway, identity-provider integration, database creation, EF migration, source-code refactor, package install, App_Data edit, or JSON mutation is included in this Phase 1 design.
