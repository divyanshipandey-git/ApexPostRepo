# ADR-0014: Make reversal stock restoration retry-safe within JSON persistence

- **Status:** Accepted
- **Context:** A void or refund must return eligible sold retail stock to the transaction's branch. Updating transaction state first can leave an unrecoverable reversed transaction when the inventory write fails. Updating inventory first can leave stock restored while the transaction remains paid if its later write fails.
- **Decision:** Restore all eligible SKU quantities in one `inventory.json` mutation before persisting the reversed transaction. `JsonInventoryRepository` records the transaction ID in a process-local set only after the inventory mutation succeeds. If the transaction write then fails, a retry sees the paid transaction and the repository skips a second restoration. If the inventory write fails, the transaction is not saved as reversed and can be retried.
- **Consequences:** Ordinary persistence failures have a safe retry path, and repeated completed reversal requests are rejected by the existing transaction state rules. Inventory JSON and transaction JSON are not crash-atomic: a process termination after the inventory file commits but before the transaction file commits loses the in-memory marker. Multiple application processes also do not share the marker. Durable cross-file recovery needs a persisted operation ledger or transactional storage, which is outside this change. Sales with no eligible retail SKU references remain unrestorable.
